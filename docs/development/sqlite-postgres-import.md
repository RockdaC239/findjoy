# SQLite → PostgreSQL 数据导入操作说明

适用：FindJoy 从 SQLite 切换到当前 PostgreSQL 开发版本。工具已用合成数据验证，不代表生产导入已执行。首次生产切换仍需 Owner 明确确认发布版本和范围，通过 main push 的 GitHub Actions 发布；本说明不授权手动替换应用代码或切换线上服务。

## 1. 前置条件

- 已验证目标 PostgreSQL、独立业务库、账号权限与备份恢复；不能指向 FindFire 业务库。
- 目标库应用业务表全部为空，先运行当前版本 `npm run db:migrate`。工具不会覆盖、合并或清空已有数据；存在旧导入或新账号/订单时直接拒绝。
- 已准备 SQLite 一致性备份并验证可恢复。使用 SQLite backup API，不只复制主文件遗漏 WAL。导入工具打开已有备份文件为只读，不修改源文件，不生成备份。
- 对生产源库停止所有写入入口，排空生成任务并暂停调度，确认旧应用/旧 worker 不再写数据后，取得最终备份。不能先取早期备份再让旧应用继续服务写入，否则会遗漏之后的数据。
- 维护期间支付通知不能返回成功后丢弃，应通过失败重试与切换后主动查单补偿；这不要求删除历史订单或回调材料。

## 2. 本地或独立测试环境演练

应用运行时只使用 PostgreSQL。`SQLITE_IMPORT_PATH` 是待导入备份的绝对路径，`DATABASE_URL` 是目标 PostgreSQL 连接串，两者必须明确配置。导入不得拿生产数据库做测试。

脚本不会自动读取 Next.js 的 `.env.local`。可通过已有安全环境注入 `DATABASE_URL`，或用 Node.js 的 `--env-file` 读取受保护的环境文件；不要在 Git、终端记录或文档填写真实凭据。

```bash
# 已由当前进程的受保护环境提供 DATABASE_URL。
npm run db:migrate

# 将示例路径替换为已验证且冻结写入后的备份文件。
export SQLITE_IMPORT_PATH='/absolute/path/confirmed-backup.db'
FINDJOY_IMPORT_WRITES_FROZEN=yes npm run db:import-sqlite
```

如果选择环境文件，可使用 `node --env-file=.env.local scripts/migrate-database.mjs`，以及在设置上述源文件路径和冻结标记后使用 `node --env-file=.env.local scripts/import-sqlite.mjs`。冻结标记只是操作人员的显式声明，工具无法代替源应用停止写入的核验。

成功输出仅包含每张源表的导入行数、是否转换旧次数和验证结果；失败输出仅包含固定阶段名称，不包含用户正文、支付材料或数据库错误参数。命令退出非零必须停止切换，不能忽略错误继续发布。

## 3. 工具保证与拒绝条件

- 以只读 SQLite 事务取得一致快照，执行 quick_check；要求包含 lives、transcripts，未知源表或未知列拒绝导入，防止遗漏新业务数据。
- 验证 PostgreSQL 迁移文件与历史 SHA-256 一致；获取迁移锁和业务表写锁，在一个事务内导入、校验和记录标记。
- 保留原有全局 UUID、人生/订单 ID、交易号、幂等键、时间、JSON 文本与账本 ID；旧无归属人生保留 user_id=NULL，不根据浏览器缓存或手机号分配给新用户。
- 原始源列按确定顺序计算内容摘要并与目标查询逐行对照，检查行数；仅对已知历史新增列使用目标默认值。JSON 字段校验可解析，不把用户正文输出到日志。
- 若源 joy_migrations 已有 points-v1，积分原样导入；否则仅账户余额/预占、账本 delta、订单权益按 1 次=20 积分转换。订单 amount_fen、付款请求和平台交易号保持不变；旧操作缺少 cost_points 时使用历史每局 20 积分的默认值。
- 核对各账户 available+held 等于账本净额，held 等于 pending 操作成本之和；核对人生、转录、账户、订单、支付记录、生成租约和结局归属关系。存在无法解释的差异则整批回滚，不能为了迁移成功直接修改余额或补一条无依据流水。
- 将账本自增序列推进到已导入 ID 之后；记录 points-v1 和 sqlite-import-v1。再次运行会因目标非空拒绝，不会二次换算或发放积分。
- 首发数据量小，当前逐行写入并在内存读取目标表计算摘要；更大库需要先演练耗时和内存，必要时升级批量流式实现。目标写入需全程冻结，不能把该工具用作在线双写同步。

## 4. 切换前后核验

1. 归档无敏感正文的验证报告：候选提交、schema 版本、源备份时间、导入表行数、单位换算口径和恢复测试结果。
2. 生产迁移窗口内执行最终备份和已演练导入，仍不开放流量；确认输出 verified=true，核对账号数、人生/转录数、订单金额/状态及积分总额。
3. 通过已获授权的 GitHub Actions 发布兼容 PostgreSQL 的版本；所有入口与调度连接同一新库，旧源进程不再写入。
4. 验证真实账号登录、普通模式开局/推进/恢复、历史归属，以及已授权范围内的支付与主动查单补偿。旧无归属人生不会出现在新用户列表，属于预期隔离。
5. 新库已有写入后，禁止直接切回旧 SQLite 或覆盖旧备份。故障时暂停相关业务，保存新库与日志，优先部署兼容 schema 的修复版本；回迁必须另行制定包含新订单和积分的全量核对方案。

## 5. 开发验证

```bash
TEST_DATABASE_URL='postgresql://findjoy_test@127.0.0.1:55439/findjoy_test' npm test -- lib/sqlite-import.test.ts
```

测试使用独立随机 schema 和临时合成 SQLite 文件，覆盖旧无归属存档、次数/积分两种口径、原订单金额和账本序列保留、重复导入拒绝、外键失败回滚、未知表/非空目标拒绝及账本不一致回滚。不使用真实用户资料或支付材料。
