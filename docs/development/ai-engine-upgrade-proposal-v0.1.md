# 人生 AI 引擎系统升级方案 v0.1

日期：2026-11-03。状态：研究后的设计提案，待 Owner 评审；不是已实现能力，不授权生产发布。

## 1. 要让玩家期待什么

让玩家愿意继续，因为“我在乎这些人，想知道自己的选择后来怎样”；愿意再开一局，因为“这次会遇见不同的人生”。积分收入建立在单局值得、下一局有差异之上。

把“上瘾”转成可验证的体验目标：进入处境、在乎人物、选择有代价、后果可辨认、未来有期待、终局有回响。时长变长不一定更好；长等待、理解困难也会拉长时长。

继续遵守：不评判幸福、不设统一成功分、无人物姓名、不预设玩家性格、不把苦难当钩子。一次开局付费覆盖同局继续、恢复与回顾，不在悬念处追加收费。不改变价格、权益或当前开放模式。当前代码 `lib/modes/catalog.ts:isLaunchModeAvailable` 仅放行普通模式；早期文档“普通+剧本开放”已落后。剧本、主题、ForU的研究与测试属于保留能力的兼容验证，不代表此次开放。

其他待评估项：上一选择是否被忽略、NPC是否只有称谓没有诉求、钩子是否不回收、每幕都逼迫大转折、选项是否存在明显标准答案、死亡分布和回顾是否失真。它们是评估清单，不宣称全部已发生。

## 3. 三条路线与选择

1. **只改提示词**：成本最低，适合先消除冲突和示例偏置；无法可靠维护人物事实，也不能保证题材分布。
2. **轻量调度 + 单次生成 + 事实与线索记录（推荐）**：程序选择机会环境、当轮需关注的后果/人物/线索，模型负责具体场景和选择。默认每轮仍一次模型请求；渐进补充必要状态。
3. **多模型导演组，先规划再写作再审稿**：有潜力，但每轮增加等待、费用与失败环节。首轮不做；仅在离线评测中按需使用独立审稿，不能默认加入线上链路。

推荐分期推进第2条，以第1条作为可单独验收的第一步。不预写整局结局，不把三幕式固定成人生必经路线。

提示词优先关系应明确：产品与安全边界、已确认硬事实、玩家已作选择、玩法约束、编剧建议、风格偏好。选择代表行动，不意味着世界必须让行动成功；NPC仍可拒绝。外部资料和历史模型文字不能覆盖规则。

## 5. 编剧能力压缩成五件事

以上来源提供方法与工具，没有提供FindJoy互动人生或付费提升的实验证据。4个人物、3条事项、2～4节点检查等均是本方案提出的初始工程预算，需实验调整。

### 5.1 每幕有欲求、阻力和变化

一幕至少让关系、资源、认识、位置或承诺发生一种变化。阻力可以是现实限制、不同诉求或内在犹豫，不必每次争吵或遭灾。温暖节点也能成立：学徒第一次被师傅托付钥匙，关系从被照顾变成被信任。

用户看见具体场景；后台只需要短任务摘要，不输出完整剧作分析，不新增面向玩家的解释面板。

### 5.2 先回应选择，再提出新处境

下一节点让玩家看见行动已发生、遇到何种回应、留下什么后果。避免只写“你选择了A”后立即换题。不要求所有节点全由玩家导致，意外仍然存在。

例：玩家拒绝异地升职，留下照顾家人。下一节点可以是同事已经离开，而家人开始要求独立；玩家获得陪伴，也面对自己被照护角色困住的可能。不能偷偷改写成玩家已接受升职。

### 5.3 选项是行动与取舍

每个选项都可实施，至少两个方向有各自合理的收益和代价；第三项可省略，不自动给“两全其美”。同一事件下不同选择应改变至少一项后续行动、关系回应、资源或承诺，不只换同义句。

不在选项里揭晓确定结局或加减数值；让当下可知的风险清楚，未知后果保持未知。放松“每次必须换价值轴”的机械轮换，防止为轮换而抛弃合理的连续冲突。

### 5.4 人物有自己的诉求

小规模常驻人物即可：先支持最多4个活跃人物，按内部ID区分不同同事/朋友，展示仍用角色称谓。每人记录与主角关系、自己的当下诉求、已确认事实和最近关系变化。不建NPC自治Agent，不模拟完整社会。

别人不知道的事不能突然拿来对质；已故人物不能在当前时间重新行动，回忆须标明。对主角心理只作可修正观察，不预先给“创伤/缺陷/必须成长”的人设。

### 5.5 少量未完事项，有兑现也有放下

维护最多3条活跃线索：来源事件、涉及人物、目前状态、上次推进节点。每轮可推进一条，也允许休息节点；每2～4个决策节点检查最久未处理的线索，决定推进、结清或自然失效，而非强制制造反转。

没有埋过的秘密不强行回收；不是每个物件都成为伏笔。死亡是终点，允许遗憾与未完成，回顾不能伪造圆满。

## 6. 多样性：改变机会环境，而不是抽签决定终身职业

普通人生开局增加轻量机会条件的采样：生活环境、可接触的行业/社会场景、家庭资源与限制、关系压力、第一件具体事情。使用少量人工审阅的材料池与权重，不依赖模型自行声明“这次要随机”。

材料池应覆盖制造维修、物流服务、照护、公共服务、普通办公室、农业与小生意等，也保留体育艺术；这是编辑上的覆盖目标，不宣称人口统计真实性。儿童不能被预设成年职业或性格。种子可因玩家选择改变，不是命运脚本。

职业之外，记录冲突机制：资源分配、信任、边界、身份认同、规则与例外、照护、合作、机会成本等。跨局重复摘要使用“处境+行动困境+关键转折”，而不只记录职业词。

优先在生成前降权最近用过的机会条件；模糊的语义相似先用于离线报告与软提醒，不接每轮向量数据库，不以关键词直接否决合理的玩家选择。相同作者剧本可以共享第一幕，但第二轮以后应体现分支差异，不把开场相同算撞车。

旧的职业硬禁用应在对比评测通过后缩减：同职业不同人生应允许，主动回归旧业也应允许；保留精确连续复述的检查与事实边界。

## 7. 状态与请求的最小增量

继续一套LifeState、一套事件循环和`scenario`玩法信封。建议给LifeState增加可选、独立版本化的`narrative`记录，包含采样条件、活跃人物和活跃线索；这不是新的平行存档或模式store。具体类型在实施设计中锁定，不滥用仅容纳标量的flags塞复杂对象。

每轮流程：

```text
已保存事实 + 上一选择 + 活跃人物/线索
  → 本地构建当轮短任务
  → 现有context组装messages
  → 单次流式生成
  → 校验事件及必要的事实/线索变更
  → applyNextEvent生成候选状态
  → 在现有事务中一起提交状态与转录
```

后台短任务可包含：本轮优先回应的选择、相关人物、建议事件功能、需检查的未完事项、近期重复模式。它是写作约束，不提前确定玩家选择、死亡或结局。任务生成不能偷偷写入已确认事实。

第一阶段不改模型协议。第二阶段需要人物事实/线索结构化增量时，再设计输出v3与变更白名单：人物ID/关系、存活与知识变化、线索来源和状态；必须有大小上限、引用校验、合并规则。模型不能直接覆盖全量状态。金额/职业等已有事实继续走现有objectiveChanges，避免两处冲突。

新输出保留当前SSE优先级：outcome/timePassed/story先出，标题和选项随后，后台元数据在后。以现有字段定义为准，不擅自重排。流式内容是候选，最终成功保存的节点才是事实；失败重试要清理预览，不能把未通过的候选当作记忆。

旧存档缺少narrative时取空记录，尽量从已有结构化历史恢复可证明事实，不把推测变成事实。历史转录兼容必须显式设计：读取v1/v2，v3启用混合历史说明或确定性转换，不能升级解析后继续混入相互矛盾格式。无转录存档保留history路径。写入失败不得只存人物记录、漏存事件或重复扣积分。

关系事实是最先值得增加的状态能力：分别表示父母的状态、子女与重要关系，避免正文说父亲离世而下一轮状态仍是父母健在。与活跃人物记录只保留一个事实来源，不能双写互相覆盖。

时间精度先不改：在现有整数年推进中选择关键结果，允许回顾解释期间变化，不虚构“当天连续几幕”。短时间危机体验如果仍不足，再独立设计月份/事件时间，不用timePassed=0绕过当前规则。

## 8. 轻量提示词改写原则

将冗长硬约束整理成：固定产品契约、阶段任务、模式边界、结构格式、少量叙事检查。后台每轮任务放user结构化边界内，固定system尽量稳定；用户自述继续是资料，不参与指令拼接。

优先处理：成人提示词中通用开局要求与剧本/ForU零时间开场的冲突；全程重大节点与普通生活温度的矛盾；剧情延续与强制换轴/禁止返回旧业的矛盾。死亡保持v2既有语义，不因新鲜度或回收线索而否决死亡。

候选写作任务（原创设计，非引用）：

> 写人生中的下一幕。以已确认事实为边界，让上一行动获得可辨认的回应。选择一个当前真正有变化的处境，用少量动作、对话和细节呈现。若本轮有选择，给出2～3个可实施且代价不同的行动；不要替玩家决定价值观。延续相关关系，避免复演刚解决的困境。只按事件协议输出，不输出分析或检查清单。

先对固定艺术创业示例做“移除叙事实例，仅留格式”实验，再与少量跨行业、跨冲突示例比较。不一次塞入大批职业样例，不默认更多示例更好。

## 9. 验证：先证明好玩，再谈转化

### 9.1 样本与预算

完全使用合成资料。第一轮每版本12个开局（覆盖普通出身；剧本按同一入口对比），筛掉明显退化。第二轮每版本6局，每局最多12个决策节点，配对测试A/B不同选择；12个节点是中程评测，不冒充完整一生。

最终候选补每版本3局完整人生，覆盖早逝、正常长寿、超长局恢复等测试情形；真实模型死亡分布需更大样本，不能用这几局推断。主题/ForU只做兼容性合成样例，不开放入口。

运行真实模型前明确模型版本、输入输出单价、调用数与预算上限，记录重试总费用、首段可读故事延迟及整轮延迟。不要擅自消耗付费API。改提示词、采样、记忆分别做消融，避免一次全改后无法归因。

### 9.2 评价表

| 目标 | 方法 | 初版验收建议（尚无基线） |
| --- | --- | --- |
| 少撞车 | 两名审阅者盲看开局/轨迹，标注相同困境与转折，分歧复核 | 重复率相对基线降低至少30%；同时报告样本数和分歧，不宣称统计显著 |
| 身份更多样 | 分开统计机会条件、成年职业、非职业身份；体育艺术不含业余爱好 | 先测基线再定配额；不以强行转职业换覆盖率 |
| 选择有后果 | 同状态两个选项各续2轮，盲审是否可辨认不同结果 | 至少80%配对存在实质差异，非同义改写 |
| 连续性 | 人工核对人物、年龄、地点、承诺；程序检查已结构化事实 | 固定合成回归中关键硬事实矛盾为0；真实故事另报缺陷率 |
| 线索回收 | 按来源事件核对推进与结清 | 不出现没有来源的“回收”，不把未完线索全部强结 |
| 沉浸感 | 隐藏版本名，按1～5评价在乎人物、想看后果、愿再来一局，记录理由 | 候选优于基线且没有靠灾难堆叠获得偏好 |
| 可靠性/性能 | JSON成功、修复、重试、兜底、延迟和全尝试费用 | 不增加默认模型请求次数；p95延迟与单局成本原则上不超过基线20%，小样本p95仅作筛查 |

这些是工程评审门槛建议，需依据基线和预算确认，不能当成已取得的提升。

### 9.3 产品指标

上线后用匿名的版本与漏斗计数：开局成功、到第3/第8决策节点、主动恢复、到达回顾、再次开局、赠送积分用完后首次购买、复购。商业化价格和扣费规则保持一致再比较；区分新老玩家与入口。长寿局和早逝局分开看完成率，避免死亡差异造成假提升。

不采集剧情、人物细节、ForU原文或完整提示词；当前诊断中有raw输出记录，实施前应移除/脱敏生产日志中的故事内容，只保留错误分类、模型与用量等必要元数据。转化提升是待验证假设，不承诺通过编剧优化必然付费。

## 10. 分期交付与影响范围

| 阶段 | 交付与主要落点 | 验收后再继续 |
| --- | --- | --- |
| P0 基线 | 合成评测数据、失败分类与盲评表；复用preview，审查提示词冲突 | 能复现Owner反馈的模式，拿到延迟/成本和质量基线 |
| P1 提示词与机会多样性 | `prompts/*.md`、`assemble.ts`、`output-format.ts`示例、`background.ts`、`storyline.ts`及现有开局/modes接线 | 少撞车、无身份强制、旧存档恢复和v2协议通过 |
| P2 后果与关系记忆 | `context.ts`、`life.ts`、`event-contract.ts`、输出/流解析协议与序列化、存档及start/next事务；按需新增轻量narrative模块 | 分支有差异、事实稳定、刷新不丢失、不重复应用变更 |
| P3 节奏与回顾 | 本地当轮任务、线索回收、`ending.md`和结局消息；普通/剧本分别调优 | 平静与压力有变化，回顾引用真实选择，死因/年龄以状态为准 |
| P4 小范围验证 | 经Owner指定范围，在test验收后按现有main/GitHub Actions流程发布 | 转化与体验数据支持保留；退化则切回旧生成版本 |

测试同步覆盖：domain转换、选择归属、模式开场、年龄边界、death空选项、协议往返、渐进读取、旧history/转录、新字段缺省、重复请求/并发/事务失败、收费与退款不变。涉及模式时核对启动、顶栏、历史、恢复、回顾问题；不借机改UI。代码交付前运行npm test（独立TEST_DATABASE_URL）、typecheck、lint、build；提示词有意变化审查preview后更新哈希基线。

运行版本必须可追溯。模型协议版本、提示词版本、存档narrative版本分别记录，不能混为一谈。P1可切回旧提示词；P2新存档不能靠Git回退盲目读取，应保留旧字段、采用增量兼容读取，上线前验证回退路径。不为此引入通用协议迁移框架。

首轮明确不做：向量库、完整世界模拟、NPC Agent集群、每轮多模型导演组、小说工程文件系统、固定英雄成长/三幕结局、月度时间系统、支付改价、新玩法上线。先证明同一引擎能把普通人的一次选择写得令人惦记。
