# 退款、积分调整与支付回调验收

## 当前边界

退款和部分退款的权益回收规则尚未由 Owner 最终确认，因此系统**不会**根据退款通知自动扣减积分、改订单状态或撤销存档。代码只做两件事：

- 校验平台签名、应用标识、事件 ID 与事件类型；
- 把退款/拒付/未知财务事件原样写入 `joy_payment_review_events`，状态为 `pending`，返回成功停止平台无效重试。

没有人工确认前，任何财务事件都不改变余额。已消费积分、部分退款和跨周期补发属于业务政策，不能由工程默认值代替。

## 数据与查询

```sql
SELECT event_id, event_type, order_id, status, created_at
FROM joy_payment_review_events
WHERE status = 'pending'
ORDER BY created_at;
```

`payload` 保存签名校验后的原始事件，仅用于对账和复盘，不进入普通日志、响应或第三方分析。重复事件按 `event_id` 幂等，不重复入队。

## 人工审核流程

1. 在平台商户后台核对退款单号、原订单号、退款金额、币种和退款状态；不要只看本地通知。
2. 在 `joy_orders` 核对原订单金额、权益数量、支付状态和平台交易号；确认不是重复订单或测试单。
3. 查看该用户账本与已消费局数，判断是全退、部分退还是仅补发。规则未确认时先记录决定，不要直接改 `joy_accounts.available`。
4. 用受审计的调整命令执行，`--reference` 使用客服工单/退款单号，保证同一原因同一引用只入账一次：

```bash
# 先 dry-run，不写账本
DATABASE_URL='postgresql://...' node scripts/adjust-points.mjs \
  --user=<user_id> --delta=-100 --reason=manual_refund \
  --reference=REFUND-20261102-001 --event=<event_id>

# 确认输出后加 --apply；同一事务会把复核事件标记为 reviewed
DATABASE_URL='postgresql://...' node scripts/adjust-points.mjs \
  --user=<user_id> --delta=-100 --reason=manual_refund \
  --reference=REFUND-20261102-001 --event=<event_id> --apply
```

- 只通过 `joy_ledger` 追加记录并更新余额，不直接改余额。
- 扣减不能使可用积分变成负数；`held`（开局预占）不受人工调整影响。
- 同一 `reason + reference` 重放不会重复入账；引用被不同金额复用时直接拒绝。
- 若积分已被消费、无法足额扣回，不要强行制造负余额；按 Owner 确认的补发/线下退款方案处理，并保留工单记录。
- 复核事件与账本调整在同一事务内完成；`--event` 不存在或已复核时命令失败。

## 生产支付回调验收方案

真实收款启用前，由 Owner 明确范围后执行；本文件不授权直接切生产或收款。

1. **准备**：使用独立测试库和独立服务实例，`FINDJOY_PAYMENTS_MODE=demo` 先跑通页面；确认 `/findjoy/api/health` 通过、迁移为最新、备份/异机/告警已配置。
2. **回调地址**：用 HTTPS 隧道或独立测试域名配置平台回调，验证 `FINDJOY_APP_ORIGIN`、nginx 转发和 `X-Real-IP`；不使用生产用户数据。
3. **签名与幂等**：依次验证正确签名成功、重放同一事件只到账一次、篡改原文/金额/应用 ID/签名被拒绝、进程重启后重放仍幂等。
4. **状态与异常**：验证关闭/失败不会覆盖已成功订单；退款/拒付进入待复核队列且余额不变；未知事件保留原文并可人工处理。
5. **金额与订单**：用最小金额测试真实首单，核对订单金额、权益数量、平台交易号、账本流水和余额；再验证主动查单与对账定时任务能补齐丢失通知。
6. **退款演练**：在平台后台发起测试退款，确认事件入队、人工审核、调整命令 dry-run/apply、复核状态和账本各一次，记录事件 ID、订单 ID、金额与前后余额。
7. **回退**：异常时先暂停新生成/收款入口并保全订单事件；不删除订单、账本或复核记录，不用恢复旧数据库备份覆盖新交易。

验收记录至少包含：测试时间、服务版本/commit、数据库版本、回调地址、事件 ID、订单 ID、金额、重复投递结果、余额前后、操作人和结论。未完成上述项目前，`FINDJOY_PAYMENTS_MODE` 保持 demo，不启用真实收款。

## 仍待 Owner 确认

- 全退/部分退款分别如何回收已消费与未消费积分；
- 异常早逝、模型失败、重复开局等场景的补次或退款标准；
- 退款时限、客服工单字段、对外展示文案与财务对账口径。
