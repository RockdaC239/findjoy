# 上线前后端与数据库完善清单

更新日期：2026-11-02。状态：待实施、待验收；不是已上线能力说明。

目标：在单人创业预算下，以服务器自部署 PostgreSQL 承接 FindJoy 正式体验和收费，并能在宣传带来突发访问时保护存档、交易与模型预算。保留现有 Next.js 后端，为 FindFire 后续统一身份保留边界。

本次只编写文档，不迁移数据库、不修改服务器、不发布。勾选必须附上验证结果，不能因为代码存在就认定上线完成。

## 1. 已确定的取舍

- 当前阶段不购买托管数据库，采用服务器自部署 PostgreSQL；收入与用户量增长后再评估托管。
- 先核实 FindFire 已有实例是否真实运行、版本与资源是否合适；适合则复用实例，两产品使用独立数据库与账号权限。不直接照搬开发 Compose，也不直接开放对方业务表。
- 保留 FindJoy Next.js、FindFire FastAPI，不拆微服务，不引入 Kubernetes、通用计费平台或消息中间件集群。
- 保留全局 UUID、独立业务与权益原则；公共身份映射只有一个权威来源，账号资料的维护归属不能因为同实例而模糊。
- PostgreSQL 不是无限容量保证。模型并发保护、备份恢复和压测与迁库一起完成。

前置约定：[两产品关联与统一身份协作约定](findjoy-findfire-shared-identity.md)。现有登录与支付操作参考：[运行说明](authing-xiaodou-operations.md)。发生冲突时区分历史记录和最新实现，不按旧段落直接操作。

## 4. 阶段二：PostgreSQL 与应用迁移（P0）

### 4.1 实例与访问权限

- [ ] 使用受支持的 PostgreSQL 大版本与经过验证的补丁版本，固定镜像版本；不为 FindJoy 接入顺带升级 FindFire 的数据库大版本。
- [ ] 数据卷、备份和密钥置于源码发布目录之外，代码同步与容器重建不删除数据；配置进程重启和日志轮转。
- [ ] 删除默认生产密码，从受保护的部署配置读取凭据。应用账号不使用超级用户；FindJoy 与 FindFire 不能读写对方业务库。
- [ ] 数据库不对公网开放。宿主机连接时绑定回环地址；容器连接时使用受限容器网络，结合安全组、防火墙与 PostgreSQL 访问规则验证边界。
- [ ] 配置有上限的连接池、连接等待、SQL 超时及空闲事务超时。各进程池总额为数据库预留维护和恢复连接，不按每个 HTTP 请求新建连接。
- [ ] 数据库不可用时返回明确的暂时不可用状态并报警，不改用内存继续接单或保存用户数据。

验收：从公网无法访问数据库；两个产品账号无法访问对方业务数据；实例重启后数据仍在；连接池耗尽时请求有界失败。

### 4.2 FindJoy 代码与事务迁移

实施主要入口：`lib/life-store.ts`、`lib/identity-store.ts`、`lib/commerce-store.ts`、`lib/life-generation.ts`、`lib/rate-limit.ts`、`lib/auth.ts`，以及实际引用这些模块的 API、页面和测试。实施时重新搜索全部调用方，不能把本清单当作完整调用图。

- [ ] 选用成熟 PostgreSQL Node.js 驱动，实现异步存储调用并更新全部调用方；测试以真实测试 PostgreSQL 验证事务，不只 mock SQL 返回值。
- [ ] 建立版本化增量迁移；结构检查、建表和一次性积分转换从正常请求路径移出，迁移失败不得启动新版本。
- [ ] 保留现有全局 UUID、人生 ID、订单 ID、平台交易号、积分单位和幂等键；时间、整数金额、布尔值、JSON 和唯一约束显式映射。
- [ ] 每个事务使用同一数据库连接。模型调用与支付网络调用不占用长事务，不在等待外部响应期间持有行锁。
- [ ] 用条件更新、唯一约束、行锁等保留并发语义：积分不能超扣或重复发放，单局不能被两个生成任务覆盖，过期任务不能迟到提交。
- [ ] 保留原子边界：人生与 transcript；支付事件去重、订单成功与积分发放；开局预占/成功消费/失败释放。
- [ ] 处理重复请求的参数冲突和事务重试；重试数据库事务不得重复调用模型、下单或发放积分。
- [ ] 采用适用于 PostgreSQL 的索引与查询，覆盖用户历史、订单、待处理操作及过期清理；列表有分页或明确上限，不读取整库 JSON。
- [ ] 移除 SQLite 专用 pragma、checkpoint 与请求期迁移，不机械翻译 `INSERT OR IGNORE`、`changes` 或 `.immediate()`。

验收：多人并发开局、同单重复回调、同局双击、跨用户访问和过期任务写入测试通过；四种模式的既有规则保持不变，未开放模式不得因迁库开放。

### 4.3 存量数据迁移与切换

- [ ] 先做 SQLite 一致性备份，使用 backup API 等支持在线一致性的方式，不能只复制主文件遗漏 WAL。备份先恢复验证。
- [ ] 从实际 schema 导出所有业务与身份数据，包含会话、一次性登录事务、限流、生成租约、结局缓存、操作和迁移标记；对会话等临时数据明确选择保留或失效，不静默遗漏。
- [ ] 以可重复、失败停止的脚本导入测试 PostgreSQL；校验行数、主外键、孤立记录、订单金额/状态、逐用户积分和账本，抽样验证人生/对话内容。校验输出只保留 ID、数量和差异摘要。
- [ ] 核实 `points-v1` 已执行状态；迁移不能把积分再次乘 20。保留订单历史金额、权益快照和预占成本，不按当前售价重算。
- [ ] 优先采用短维护窗口切换，不做双写：停止所有写入来源、排空生成任务，暂停调度；支付通知由可重试失败响应和后续主动查单补偿承接，不得返回成功后丢弃通知。
- [ ] 冻结后做最终导出、导入和校验，部署兼容新库的版本，再逐步恢复入口、调度与支付回调处理。切换期间发生的支付必须查单补齐。
- [ ] SQLite 原库与最终备份只读保留，核实所有入口均已切到新库，禁止新旧实例分别接写入。

验收：同一批脱敏核验指标迁移前后一致；旧账号能恢复原人生与积分；过期或取消的生成不会重新扣费；维护窗口内付款能补偿入账。

## 5. 阶段三：突发流量与成本保护（P0，迁库不能替代）

- [ ] 为开局、推进、结局生成增加全站在途模型请求上限，覆盖重试与多进程；另加每用户频率/在途限制，保留单局锁。达到上限时短暂有界等待或直接提示繁忙，不建立无限队列。
- [ ] 准入拒绝发生在扣积分和调用模型之前；开局已预占后发生失败则按原操作释放。前端可理解 429/503，按提示等待，不自动无限重试或自动换开局幂等键。
- [ ] 超时、重试总时长、生成租约、代理超时互相匹配；重试也受并发/预算限制。已向用户报繁忙或失败的任务不能无约束继续生成。
- [ ] 确定浏览器断流后的行为：继续生成则保持容量占用并允许恢复查询；取消则可靠释放租约与预占，不让连接断开绕过限制。
- [ ] 限制请求体、ForU 自述及输入字段长度，限制列表返回量；敏感资料不进入日志、压测样本或第三方分析。
- [ ] 设置模型供应商消费额度/告警，记录成功、失败、重试与降级次数。若没有可靠每日硬预算，则用低并发和可操作的“暂停新生成”开关控制风险。
- [ ] 登录、订单查询、支付重试限流一起验证；可信代理覆盖真实 IP 请求头，不能信任公网自报 IP。现有限流落库自身也需计入写入压力。
- [ ] 过期操作清理按批次执行，设数量/耗时上限并建立索引；不要在单次开局内清理全站历史积压。

验收：超过容量时有明确繁忙反馈，不超扣、重复开局或持续堆积内存；模拟模型 429/超时/断流仍能恢复已提交状态。

## 6. 阶段四：账号、支付与隐私（P0）

- [ ] 在实际 HTTPS 域名完成 Authing 登录、回调、刷新、会话过期与退出；确认 Cookie 属性、来源/CSRF 校验和非敏感错误响应。
- [ ] 用两个测试账号验证人生、历史、订单、账户编辑、操作查询与结局的所有权。旧无归属存档不能凭 lifeId 认领。
- [ ] 生产使用服务端模型配置，禁用本地配置写入口，审查模型列表等辅助接口是否需要关闭/鉴权/限流；用户请求不得改变服务端密钥或任意上游地址。
- [ ] 核验模型转录、ForU 自述、手机号、Cookie、支付链接、签名原文和私钥不进入生产日志或监控正文；明确存储和向模型传输的告知边界。
- [ ] 真实收费单独验收：价格/赠送积分/降级收费规则确认，微信下单付款、验签通知、重复通知、查单补偿、页面断网恢复通过；本地首单不替代公网 webhook 验收。
- [ ] 确定退款和积分调整规则，首期允许人工处理但必须有可追溯流程，不直接改余额；明确已消费积分、未消费积分与部分退款如何核对。
- [ ] 安装可信对账调度，验证积压超过单批处理能力时可在目标时间内清完，长期 UNKNOWN 和未到账订单能通知 Owner。
- [ ] 未通过真实收费验收时保持 demo，不收款；免费体验上线也必须通过数据归属、过载和备份验收。

FindFire 正式接入另开任务：复用唯一身份映射，迁移旧 `rocc`/UUIDv5 数据，完成 FastAPI 鉴权与对象归属；不得靠相同手机号自动合并账号，也不把 FindJoy 会员/积分当成共用权益。

## 7. 阶段五：备份、观测和故障恢复（P0）

- [ ] PostgreSQL 至少每日自动逻辑备份，覆盖业务库与恢复所需角色/权限配置；备份加密或存于受限存储，记录成功/失败和过期清理。
- [ ] 至少一份备份离开应用服务器，不能只放另一个本机目录。先确认可用低成本存储位置，再启用真实收费。
- [ ] 建议初期保留最近 7 天每日备份及最近 4 周每周备份；备份频率结合磁盘和数据量验证，避免备份挤满磁盘。
- [ ] 明确并验收 RPO（最多丢失多久数据）与 RTO（多久恢复服务）。每日备份只能覆盖最长约一天的数据损失；若不可接受，增加频率或部署 WAL 归档与时间点恢复，不把“每天备份”称为零丢失。
- [ ] 用独立空库演练恢复，验证账号、人生、订单与积分一致。支付可查单补偿不等于可以恢复丢失的人生或消费记录。
- [ ] 最小监控覆盖：CPU/内存/磁盘与增长、连接池等待、事务耗时/锁等待、HTTP 错误、SSE 中断、模型在途/失败/费用、支付未确认与过期预占。
- [ ] 配置磁盘不足、备份失败、数据库不可达、模型失败激增及支付积压的可达通知；只选现有轻量工具，不先建设完整监控平台。
- [ ] 区分进程存活与业务就绪：首页 200 不代表可接单。就绪检查验证数据库连接和 schema 版本，内部诊断信息不向公网暴露；备份恢复演练另验证真实读写能力。

验收：提供最近一次异机备份、恢复耗时和抽样核对结果；模拟数据库断连时停止接新业务，恢复后可继续；重启应用不会遗失已提交交易。

## 8. 阶段六：压测、发布与回滚（P0）

### 压测方法

- [ ] 独立环境使用合成用户和合成短局/长局数据；记录机器规格、数据规模、并发、到达速率和测试版本。不得用真实 ForU 自述或直接压生产支付。
- [ ] 第一轮模拟模型延迟和流式输出，测试集中登录/开局、持续推进、长存档、历史查询与支付重复回调；保留实际数据库和存储事务，不用空接口代替。
- [ ] 按 10、30、100、300 个虚拟用户逐级加压，并分别测试短时开局突刺和持续请求。数字是测试梯度，不是容量承诺；资源或错误恶化时停止升级。
- [ ] 使用小样本真实模型验证供应商 RPM/TPM、重试、超时和成本；数据库模拟压测不能证明真实模型能承载同样并发。
- [ ] 记录 P95/P99 接口耗时、首字/完成时间、实际生成吞吐、准入拒绝、错误率、连接池等待和内存趋势；把模型等待与数据库耗时分开。
- [ ] 初始验收目标：容量内非生成接口 P95 不高于 1 秒、非预期服务端错误率低于 1%；事务无超扣/重复发放/越权，持续运行无无限积压。目标可按体验收紧，不能用降低正确性换吞吐。
- [ ] 选择通过持续压测的并发上限并留资源余量；超限时快速返回繁忙且无扣费。最终记录“允许多少在途生成、每秒可接多少开局”，不用“支持多少月活”替代。

### 发布与回滚

- [ ] 运行 `npm test`、`npm run typecheck`、`npm run lint`、`npm run build`，以及新增 PostgreSQL 集成/迁移/恢复测试。界面繁忙与恢复反馈同时适配手机和桌面，无需默认提供截图。
- [ ] 修改 `.env.example`、部署登记与运行说明，明确 PostgreSQL 连接配置、迁移命令、初始化与备份方式；只记录变量用途，不提交真实凭据。
- [ ] 修复部署脚本可能覆盖 FindFire 根路由的问题，指定唯一 nginx 配置维护入口；检查 `/`、`/findjoy`、两产品 API、认证回调、支付通知及 SSE 超时/缓冲。
- [ ] 数据库迁移是显式部署步骤且失败停止；首次部署基础设施和迁移窗口单独记录，重跑不会重复导入或再次换算积分。
- [ ] 日常开发在 `test`；Owner 确认候选版本和范围后，从 `test` 合并到 `main`，通过 push 触发现有 GitHub Actions。不得手动同步源码、切服务目录或以测试分支部署绕过发布约束。
- [ ] 准备与新 PostgreSQL schema 兼容的应用回滚版本。切换后若已有新写入，不能简单切回旧 SQLite 或恢复旧备份，否则会丢失订单、积分和存档；应暂停新生成/收款，保全新数据并前向修复，必要时制定完整回迁与对账方案。
- [ ] 切换后冒烟测试登录、开局、推进、恢复、历史、积分和已授权范围内支付；验证 FindFire 页面和 API 未受影响。

验收：全部 P0 有结果记录，迁移演练和回滚兼容性已确认，Owner 明确批准发布范围后才开放真实流量。

## 9. 上线后观察与暂缓事项

上线最初 24–48 小时及每次宣传后检查错误、模型成本、生成拒绝、备份和订单对账。出现存档/积分不一致，立即暂停相关写入口，保全数据后核查；数据库或模型持续过载时降低准入，不靠无限重试维持表面可用。

以下随实际瓶颈安排，不作为首期必建项：

- P1：长局 transcript 追加存储、人生摘要字段、减少完整 JSON 往返；以压测证据决定拆表范围。
- P1：FindFire 正式接入统一身份和用户旧数据迁移；不阻塞独立 FindJoy 上线。
- P1：随交易规模提高备份频率或增加时间点恢复；若既定 RPO 要求已需要，则提前升为 P0。
- P2：收入允许后迁托管 PostgreSQL，复核数据库版本、扩展、编码、网络与备份恢复兼容性；不是保证只改连接串就完成。
- P2：有明确需求后才增加多应用实例、独立生成 worker、外部队列和数据库高可用；单机阶段先保留可控的维护窗口。
