# 游戏体验优化方案 v0.1

创建日期：2026-11-06。

更新日期：2026-11-06。

**状态：Owner 已授权按本稿实施首版并提交，开发分支 `test` 已实现核心流程，未发布。** 第 8 节记录已确认的产品结构，第 9～13 节给出技术设计与验收要求，第 14 节记录实际落地范围与限制。故事篇幅、节奏和内容质量继续通过试玩微调，不能将结构改造完成等同于体验效果已经验证。

## 1. 背景与问题

上线初期数据与判断见[上线首日体验反馈](./2026-11-05-launch-feedback.md)。数据反映推进情况，不能单独证明停玩原因；本方案进一步依据 Owner 自己试玩后的明确反馈提出。

### 1.1 Owner 的体验反馈

1. **有头没尾。** 做了决定后，不知道决定带来了什么，就进入下一个决策节点。希望用年度快照承接节点，让节点之间有生活。
2. **文本四平八稳。** AI 容易生成“你选择了创业，经过努力，公司有所起色”一类摘要，缺少具体的人、意外细节和情绪钩子。Owner 自己玩到二十多岁已不想继续。

Owner 对体验方向的表达：

> 节点是骨架，日常是血肉。玩家不是在节点上活着的，是在节点之间的日子里活着的。
>
> 把日常微循环、短回响、年度快照塞进节点之间，节点才会有重量——因为玩家在节点之间已经付出了、失去了、期待了，节点到来时才有东西可结算。

### 1.2 本轮初步判断

目前玩家做完选择，往往得到下一道题，没有充分经历自己的选择。故事中即使有生活细节，也未必形成玩家在意的人、变化和期待。

Owner 提供的 30 岁截图同时交代母亲换厂、身体状况、工艺卡、自己开始带新人等信息，但随后立即要求决定如何带人。标题“你开始带新人跑现场”重复已知事实；三个选项更接近抽象的工作态度选择，眼前具体的人与处境仍较弱。

**Owner 补充约束：截图中的事件本身质量不足，只作为问题分析材料，不作为优化样例或验证题材。后续重新选题，不沿用该事件及其人物、分支或改写。**

这些是对当前样例的体验判断，不代表每局都如此，也尚未确定所有技术根因。

## 2. 目标与方案取舍

建议将体验的基本单位从“一次人生决策”改为“一段有起因、有生活、有结果的经历”。玩家应能感到：自己的行动改变了生活，故事里有人值得在意，还有事情值得期待。

| 方案 | 优点 | 主要局限 | 本轮建议 |
| --- | --- | --- | --- |
| 仅优化文风与提示词 | 改动较小 | 可能只得到更漂亮的履历摘要，选择仍无充分后果 | 不作为完整解决方案 |
| 保留重大节点，补充节点间后果与生活 | 直接回应本次体验问题，可先用短篇样例验证 | 需控制篇幅、等待和操作负担 | 优先讨论此方案 |
| 完整日常模拟，增加每日活动与操作 | 可提供更多生活参与 | 开发范围大，可能将决策疲劳变成琐事疲劳 | 当前不建议展开 |

沿用“故事重于数字”的产品原则，不增加统一幸福分或成功分。四种模式继续共享人生状态和事件循环；本稿以普通模式成年体验举例，童年与其他模式的适用方式尚需讨论。

## 3. 建议的体验结构

### 3.1 先经历上一选择，再面对下一选择

建议的展开顺序：

**做出选择 → 眼前回应 → 一段日常 → 生活变化 → 新的决定。**

这是体验顺序，不要求每步都独立点击、独立页面或独立调用 AI，也不要求每轮机械地出现五段固定模板。

- 新问题出现前，至少让玩家看见上一行动的一个具体后果。
- 长期结果可以未知，但眼前回应不能缺席。
- 结果要体现玩家实际选择，不能把未选分支写成事实。
- 后续决定可以从前次行动自然生长，也可以由生活中的新变化引出，避免一生被一条事件链锁死。

回应需要让玩家清楚自己实际争取到了什么、承担了什么，以及哪些结果仍需等待，不能只抽象地评价这次决定。

### 3.2 年度快照：写日子怎样变了

快照围绕刚选择的生活呈现两三件有意义的变化，可包括反复发生的小动作、一个人的态度变化、某件期待的兑现或落空。不固定每次三项齐全，不额外堆年度总结。

不同选择应该带来可辨认的生活变化。若选什么都得到近似快照，再好的文笔也不能提供参与感。具体内容样例待重新选题后编写。

“年度快照”暂作为过渡形式名称，不代表强制每次跨一年。矛盾正在发生时可停留在同一年龄；稳定时期可跨数年。具体时间规则待讨论，并须尊重各模式既有起始年龄与时间规则。

### 3.3 日常微循环：熟悉的小事发生变化

建议先用“小事再次出现，但意义改变”建立生活感，而非增加吃饭、上班、休息等每日操作。

同一件日常小事再次出现时，应能看出关系、处境或玩家生活的变化，而非重复描写相同细节。

微选择只在玩家可能在意时出现。小选择可以影响关系，不要求每次改变人生轨道，也不能成为无影响的额外点击。是否纳入首版仍待讨论。

### 3.4 人物与戏剧性：让人在具体处境里行动

人物应有自己的诉求、顾虑和行动，不能只在需要玩家答题时充当功能角色。选项应回应眼前的事，让玩家同时在乎两件可能冲突的东西。

重新选题时，先判断场景本身是否值得经历、人物是否值得在意，再写具体选项；不能只给平淡事件增加事故或两难，就视作完成体验优化。

戏剧性不等于每幕都有事故、背叛或秘密。安稳、善意、幽默和收获同样可以让人继续读。

### 3.5 短回响与长期兑现：让期待有去处

短回响回应眼前行动；长期兑现让早先的人、物或约定在合适时机再次产生意义。

当故事建立具体约定或期待，后续应在合适时机兑现，或交代它为何变化，而非无声消失。并非所有细节都需成为伏笔，也不能无限积累悬念、每次只留问题不交付结果。

不能形成“所有好事后面必有坏事”的套路。认真教人可以真的换来信任，争取报酬可以真的成功，安稳日子可以值得停留。玩家要先经历自己争取到的东西，后续选择才有可珍惜、保护或放下的对象。

### 3.6 阅读与操作节奏

建议先呈现上一选择的回应和生活片段，再在适当位置出现新的处境与选项，给后果留出阅读空间。

- 允许快速展开，避免强制打字动画或固定等待。
- 不为营造节奏增加没有意义的“继续”按钮。
- 不用更长文字冒充更深体验。
- 具体呈现方式、篇幅和点击次数均待讨论；当前不改界面。

## 4. 与现有引擎的关系

现有代码与维护文档已包含活跃人物、未了事项、来源事件记录，以及选择回应的提示词要求，见[人生 AI 引擎维护约定](../development/ai-engine.md)。这些能力不等于玩家已获得理想体验，也不能仅凭“提示词写了要求”认定问题已解决。

建议优先复用现有结构，进一步明确：上一选择改变了什么、谁因此采取行动、什么尚未有结果、何时需要回应。记录最终必须落实到玩家读到的内容中。

经后续讨论，模型调用方式已确认，字段、协议与状态设计建议见第 9～13 节。现有结构不足的部分按该范围调整，同时处理旧存档、恢复和流式展示的兼容，不提前建设完整日常引擎。

## 5. 建议的验证顺序

1. 重新选定有吸引力的题材，再写不同选择后的连续体验，覆盖眼前回应、生活快照及一次后续兑现。不沿用截图事件，具体题材与样例规模待讨论后确定。
2. Owner 逐段判断：是否惦记某个人，能否说出自己的选择改变了什么，是否主动想看下一幕，是否觉得阅读或操作拖沓。
3. 连续样例敲定后，再验证真实模型能否稳定生成；比较不同选择的差异、事实一致性、重复程度、延迟与成本，不只挑最好的一次展示。
4. 局部体验成立后再扩大到完整人生，检查稳定生活、冲突、收获与时间跨度的节奏。
5. 后续线上用推进深度、回访继续、完成后复玩及真实玩家反馈观察效果，不将完成率或文字长度单独等同于体验提升。具体指标口径另行确定。

## 7. 本轮边界与风险

本稿记录 Owner 的问题、已确认结构、助手提出的方案及尚未决策的取舍。第 8 节作为后续结构改造的确认依据；尚未确认的建议不视作既定需求。现有产品宪法与不冲突的玩法规则继续适用。

初稿阶段仅讨论、不实现；后续 Owner 已明确授权按当前方案实现并提交，执行情况见第 14 节。本次不迁移旧存档、不发布。

主要风险：生活片段增加后可能只有篇幅变长，阅读、点击和生成等待反而加重；强调戏剧性可能演变为强行制造事故；记忆字段齐全也可能无法产生可信的后果。需要用连续体验样例和真实模型验证分别检查。

## 8. 已确认的整体游戏结构

本节来自 Owner 明确确认，优先于前文仍开放的结构建议；Owner 随后授权按当前方案实现首版并提交，未授权发布。

### 8.1 玩家看到的流程

```text
童年讲述幕 → 第一个成年决策幕
                    ↓ 玩家选择
               结果与生活讲述幕 → 下一个决策幕
                    ↑                  ↓ 玩家选择
                    └────── 往复 ──────┘

到达生命终点：最后的讲述 → 告别幕 → 回顾页
```

- **童年讲述幕**：将成长经历在一幕中讲完，可由多段渐出文字组成，不再设置若干无选项、只能点击“继续”的童年节点。建立家庭、重要人物和成长环境，并落到第一个决策的处境。
- **决策幕**：讲清眼前需要玩家回应的具体处境，展示本次选项；不重复整段讲述，不代替玩家决定。
- **结果与生活讲述幕**：承接刚才选择的结果、经历、生活与变化，过渡到下一决策。讲述内容可以跨时间，不要求每次都写足一年或固定五段。
- **告别幕**：在最后一段人生之后承接情绪停留，继承现有告别表达；不逐字重播刚看过的死亡叙述。
- **回顾页**：回望实际选择及其后果，保留现有模式问题、保存与分享边界。

普通/主题人生仍从 0 岁建立状态并讲述成长，不能改成直接创建成年角色。“成年”在本稿指进入主动决策阶段，**本轮未确认调整年龄边界**：当前 `lib/engine/phase.ts` 的 `CHILDHOOD_BOUNDARY=15`，实施默认沿用该常量，不能擅自改为 18。改动年龄需另行确认。剧本从剧本年龄、ForU 从当前年龄开局，不强制补演童年；未开放模式不因本次改造而开放。

### 8.2 模型调用与幕的关系

| 调用时机 | 输入 | 同一次生成返回 | 展示顺序 |
| --- | --- | --- | --- |
| 普通/主题新人生开局 | 从 0 岁创建的状态、出身和模式资料，无玩家选择 | 童年讲述＋首个决策处境及选项 | 先童年讲述，再首个决策 |
| 剧本/ForU 开局 | 原有起始年龄与情境，无玩家选择 | 起点讲述＋当前年龄的首个决策 | 先起点讲述，再首个决策，不重复童年 |
| 玩家提交有效选择 | 当前状态、历史、实际选择、人物与未了事项 | 上一选择后的讲述＋下一个决策处境及选项 | 先讲述，再决策 |
| 该次生成到达生命终点 | 同上，或开局合理出现早逝 | 最后的讲述与终点信息；没有下一决策 | 最后讲述、告别、回顾 |

**一轮推进只做一次正常事件生成，不为讲述幕与决策幕拆成两次请求。** 用户点击“看下一幕”或文字播放结束，只切换已生成内容，不请求 `/next`。完整校验失败或网络失败的重试沿用异常流程，“一次调用”不表示取消必要重试。

回顾仍是现有独立结局生成，不能并入最后一次事件响应或误删。此约定针对游戏事件生成，不要求删除已有出身抽样/资料准备能力，也不新增幕后规划、人物代理或年度生成请求。

### 8.3 时间与决策权

讲述可以包含别人采取的行动和玩家已选行动的自然执行，但不能替玩家作出新的重要取舍。故事走到需要取舍处，结束讲述并给决策。

下一决策发生在本轮落地年龄；上一选择仍属于上一节点的年龄。讲述描述这两个时点之间的经历，可以有短回响、日常与较长期变化，不能把所有后果都算成决策当天发生。

保持一个 `LifeState`、一个事件循环和现有 PostgreSQL JSON 存储。不增加每日引擎、额外事件表或新依赖。只在确有需要时提取小型讲述展示组件，复用告别的文字渐出视觉，不将带回顾请求状态的整套 `Farewell` 强行用于普通讲述。

## 10. 模型契约与状态设计

本节为后续实现的具体技术设计建议。体验结构已确认；字段命名如需调整可以沿用仓库习惯，但不能丢失以下语义、兼容及验收要求。

### 10.1 输出协议 v3

建议在现有输出中增加 `narration: string`，将现有 `story` 专用于下一决策处境，避免把两段文字塞在同一字符串里靠标题或分隔符猜测拆分。不要与现有后台 `narrative`（人物/事项更新）混淆。

以下是正常成年轮次的结构示意，数字与占位文字仅演示契约，不是内容样例或质量标杆：

```json
{
  "outcome": "continue",
  "timePassed": 1,
  "narration": "上一选择的具体回应、日常与生活变化。",
  "story": "由这段经历过渡而来的下一次待决策处境。",
  "event": { "type": "random", "title": "下一决策的标题", "importance": 0.7 },
  "choices": [
    { "id": "A", "text": "可实施的行动 A" },
    { "id": "B", "text": "与 A 有实质区别的行动 B" }
  ],
  "objectiveChanges": {},
  "memory": "本轮已经发生、值得保留的具体变化。"
}
```

- v3 的 `narration` 必须非空；`outcome=continue` 时，`story` 非空且提供 2～3 个合法选项。
- `outcome=death` 时，`narration` 包含最终结果与生命终点，`story` 为空字符串、`choices=[]`，`event` 描述终点，并保留合法 `deathCause`。死亡分支先识别再校验，不因没有决策正文或选项而补造一题。
- `objectiveChanges` 是本轮从旧状态到落地状态的变更，包含讲述和决策处境中已经发生的事实，不包含任何未选行动的结果；金额增量等原有字段语义不变。
- `memory`、`narrative`、usage 沿用原语义；当前来源仍由服务端替换为本轮真实历史 ID，不由模型发明 ID。
- 输出顺序建议固定为 outcome/timePassed/narration/story/event/choices/其余状态字段，先交付可阅读内容。顺序不是信任边界，完整 JSON 仍须校验。
- 正常 v3 响应缺少讲述，应走明确诊断、必要修复/重试与有效兜底，不能静默把它当成旧 v2 合法响应。旧存档缺字段兼容与新输出的严格校验要分开。

### 10.2 历史、选择归属与来源

建议新流程人生存一个固定的 `experienceVersion: 3` 标记；历史 `LifeEvent` 与内部 `NextEvent` 增加对应讲述字段，旧记录缺省保留。标记由服务端设定，不接受玩家或模型指定。

一次生成仍对应一个历史节点：本轮 `narration` 是上一节点实际选择的后果及过渡，本轮 `story/choices` 是下一次待决策处境。提交的 `choiceId/choiceText` 继续写回给出它的上一节点；本轮节点不得因此被误标为已经选择。

不为“讲述”“决策”各调用一次 `applyNextEvent`，不产生两个重复历史节点，不重复加年龄、扣积分或应用财务变化。回顾中的真实选择数量按有实际选择的节点计算；现有 `facts.events` 如继续表示历史节点数，不偷偷改成选择数。

回顾证据应将上一节点行动关联到下一节点的 `narration`，不能继续只拿下一决策标题当作完整后果。长回顾、历史页面、摘要和分享节点都需检查新字段的读取，公开分享仍遵守现有隐私边界。

### 10.3 时间规则与开局

- 普通/主题新状态仍是 0 岁，开局 v3 讲述出生到决策入口；正常开局建议落在现有边界 15 岁，首个 `timePassed=15`，以共享常量构造和校验，不硬编码在组件里。不要沿用现有 1～8 年普通轮次上限截成 8 岁，也不要让童年跨界截断逻辑把它改成 14 岁。
- 若开局合理到达童年生命终点，按实际终点年龄返回死亡内容，不为凑首个决策强行存活到边界。常规开局仍以进入首个决策为目标，不增加早逝频率。
- 剧本/ForU 首幕仍 `timePassed=0`，遵守原有起点，不重复模拟其过去，也不将用户自述当模型指令。
- 成年 v3 普通轮次允许 `timePassed=0` 表达同龄内的短回响和连续冲突，也允许正整数跨年；继续保留普通轮次既有跨度上限，具体叙事跨度后续校准。不强制每个决定加一岁。
- `normalizeGeneratedEvent`、repair、generate 及 `applyNextEvent` 当前存在至少推进 1 年的限制，要按 v3 与开局阶段一起调整，不能只在模型示例中写 0。
- 讲述包含多个年龄时，不能沿用“将 story 第一处‘你 X 岁’一律替换为落地年龄”的做法处理整段童年或过渡。决策处境年龄对齐落地年龄；讲述中的时间按起点到终点的区间核验。界面讲述显示年龄范围或阶段，进入决策再显示落地年龄，避免读出生段时顶栏已像在描述 15 岁当下。
- 同龄事件可有多个，各自使用真实事件 ID 区分，不靠年龄去重。不额外建设月份/日期模拟系统；若多轮停在同龄而无进展，先通过内容验证校准，不用强制年增掩盖。

### 10.4 旧存档和旧转录

为减少迁移风险，建议本次先按人生固定体验版本：新建人生使用 v3；无 `experienceVersion` 的已有活动人生继续旧生成/展示逻辑，直到自然结束，不半路混合两套模型输出。

- 旧人生、旧转录、已有结局不批量改写、不删除、不重新扣费或重生内容。
- v2/v3 的消息组装、完整解析、流式解析和 mock 都按服务端人生版本选择；不能只升级全局 `MODEL_OUTPUT_VERSION` 后继续向旧转录追加不兼容的 assistant 输出。保留 v2 兼容出口，直至另有旧人生升级方案。
- 缺少转录的旧人生继续使用原有 history 路径。
- 用户恢复旧童年人生仍可看旧节点，这是兼容策略，不代表新开局仍使用多次“继续”。历史恢复应能覆盖旧成年、童年和已结束三类。
- JSON 中增加可选字段原则上无需新数据库表；如实施发现确有 SQL 迁移需求，说明依据，不为此次显示游标建表。

## 11. 前端展示、流式与恢复

### 11.1 展示状态与业务状态分开

新流程的客户端展示状态建议为：`generating → narration → decision`；终点为 `generating → terminal narration → farewell → review`。

完整响应校验并原子保存后，业务状态已落到下一决策或生命终点；玩家此时仍可阅读讲述。切幕只改变展示位置，不再推进游戏。讲述期间不要显示下一决策的选项、标题或尚未经历的状态摘要。

讲述复用告别幕的段落渐出风格，支持显示全文与 `prefers-reduced-motion`。建议全文出现后提供一个明确的“进入下一幕”动作，操作仅切换本地已生成内容；自动切幕与具体动效时间尚待讨论。无论采用哪种方式，都不能以强制等待换取时长。

### 11.2 SSE 和错误恢复

沿用 `status/token/retry/complete/error` 事件，不新增独立讲述生成接口。stream parser 要能分别读取 `narration` 与 `story`，不能靠全局匹配第一个字符串字段读取嵌套内容；处理字符串转义、分片截断、字段乱序和未完成选项对象。

可以在 token 到达时预览讲述，但它是尚未提交的内容。**只有 `complete` 确认有效持久化，且讲述展示完成/玩家切幕后，下一决策才可操作。** 后续决策已生成不代表必须提前露出。

`retry` 必须清空两部分临时文本与该次动效状态；`error` 不将半截内容写成成功结果，不保留可点击的新选项。保留上一已确认状态并提供恢复入口。新 v3 路径禁止仅因 token 中读到 `outcome=death` 就进入空白页或直接跳过最后讲述。

客户端超时、complete 丢失或旧 `expectedEventId` 重放时，先 GET 恢复服务端最新节点；若已经提交，显示已保存的这轮内容，不再次应用选择。不得因为前端没收到响应就自动重复开局或无条件再生成。

### 11.3 刷新、退出与跨设备

讲述和决策正文都存在服务端历史中，不能只保存在组件 state 或 SSE complete 的瞬时 payload 中。

建议使用一个最小的浏览器阅读游标（例如 sessionStorage 中的 lifeId＋eventId＋已进入的展示阶段），只存不含正文的标识与枚举，不存故事、自述或账号凭证。按当前人生与事件精确匹配；新事件清除旧展示阶段，退出登录清理相关游标。

- 未记录该事件已进入决策：刷新后从本次完整讲述开始，允许直接显示全文/切幕，不重请求模型。
- 已进入该事件决策：刷新恢复决策，不强制重看。
- 新设备或缺少游标：安全地重放当前已保存讲述；首版不承诺跨设备同步阅读到第几段。
- 终点游标独立区分最后讲述、告别和回顾；直接打开 review、刷新或重新登录，同样按已保存终点恢复，不遗失最后讲述。

不要把阅读游标当成游戏进度或权限依据，也不要让它触发积分变化。若存储不可用，退回可重放已保存内容的行为，不能阻断继续。

### 11.4 告别与回顾衔接

v3 的终点讲述只展示一次完整正文；告别只保留简短收束与等待回顾的状态，不再把同一整段正文交给 `farewellLines` 重放。v2 仍按原告别方式展示，不强行套用 v3。

回顾可像现有 `ReviewExperience` 一样在不可见区域预生成，并使用原有结局缓存、锁和恢复机制。回顾提前成功也不能在玩家尚未看完最后讲述时自动跳走；失败可重试回顾，不重新生成最后事件。正常讲述不得使用“正在整理这一生”等告别专属文案。

### 14.1 开篇卡住的修复与真实模型复测

首版提交后，Owner 本地出现带 v3 标记、却只保存到 5 岁且缺少 narration/选项的旧式童年首幕。前端因此显示空讲述，进入决策后又没有可选项。排查时原开发进程跨越了整次协议改造仍在运行，存在热更新后的新旧代码混用；原保存入口信任生成适配器，缺少最终版本校验，允许异常结果落盘。此前 Mock 验证未覆盖该真实开局问题。

修复：start/next 保存前使用同一严格契约再次校验，不合法的开局失败释放预占；对仅有一个旧式童年首幕的异常 v3 普通/主题人生，展示已有正文和“接着讲完童年”入口。恢复沿用原人生 ID，从当前年龄接到 15 岁，保留原历史，不伪造玩家选择、不重新收取开局积分；重建 v3 转录，原经历作为历史资料保留。系统提示明确恢复跨度优先于普通轮次 8 年限制。该入口只用于识别到的异常开篇，正常讲述切幕仍不请求模型。

已重启本地开发服务，并通过真实模型将当前异常存档从 5 岁接到 15 岁，出现 3 个可用选项；原历史保留且未替玩家选择。另以合成资料实测真实 deepseek-flash 的新开局及下一轮：分别落到 15 岁、16 岁，两轮均有独立讲述和 3 个选项，首 token 约 0.56/0.89 秒，完整返回约 10.4/7.3 秒。这是两轮样本，不代表全局延迟或留存改善。

新增回归覆盖异常开局拒绝与退款、恢复历史/转录/计费、视图恢复、系统跨度例外及 Mock 兼容。完整测试为 417 项通过；类型、lint（仍为既有 5 条本地脚本警告）、设计同步检查通过。尚未做真实模型完整人生或长期稳定性评估。
